**Версия:** 3.1 (PRD v3.0 + фидбэк PM: роли и доступы, амортизация и фонды, детализация ценообразования)
**Статус:** Draft, готов к передаче архитекторам
**Аудитория:** Project Manager, Tech Lead, архитекторы, Backend Team

**Условные обозначения**

- `[РЕШЕНО]` — согласовано с владельцем продукта.
- `[ПРЕДЛОЖЕНИЕ]` — предложено бизнес-аналитиком, требует подтверждения (см. реестр открытых вопросов, раздел 12).
- `CFG` — конфигурируемый параметр. Значение в документе задаёт значение по умолчанию. Все `CFG` хранятся в конфигурации (не в коде) и меняются без релиза.

## 1. Описание продукта и цели

### 1.1. Описание

Smart Rent Hub — платформа, где физические лица арендуют профессиональное A/V-оборудование, бронируют онлайн и забирают технику на пункте выдачи. Платформа управляет доступностью, ценой, рисками порчи и AI-подбором комплекта.

### 1.2. Ключевые проблемы

1. **Овербукинг** — срыв съёмки из-за двойного бронирования.
2. **Порча и невозврат** дорогой техники без создания непомерных финансовых барьеров для клиента.
3. **Сложный подбор** совместимых комплектов для неспециалистов.
4. **Непрозрачная цена** (износ, спрос).

### 1.3. Бизнес-цели и метрики успеха

| Цель | Метрика | Целевое значение (ориентир) |
|---|---|---|
| Исключить овербукинг | Доля броней, не выданных по вине платформы | < 0.5% |
| Не допустить безвозвратных потерь | Loss ratio (убытки от повреждений и невозврата / сборы за защиту и штрафы) | < 60% CFG |
| Не создавать барьеров | Конверсия «начало оформления → оплата» | > 35% |
| Полезный AI | Доля AI-подборок, положенных в корзину | > 25% |
| Загрузка парка | Утилизация единиц (дни в аренде / доступные дни) | > 50% |
| Скорость склада | Среднее время инспекции возврата | < 2 ч |
| Окупаемость парка | Срок окупаемости единицы по управленческому учёту (5.12.5) | ≤ 12 мес `CFG` |
| Маржа после фондов | Выручка − отчисления в фонды − прямые расходы | > 25% `CFG` |

### 1.4. Учебные цели (что должна демонстрировать реализация)

| Технология | Бизнес-сценарий | Чему учимся |
|---|---|---|
| Ёмкость SKU, Redisson, блокировки | Бронирование без овербукинга | Конкуренция на «горячем» счётчике, сравнение стратегий блокировок |
| Сага + Outbox | Резерв → риск → оплата → подтверждение | Компенсации, идемпотентность, таймауты |
| Debezium + Kafka | Синхронизация индексов, события заказа | CDC, outbox, идемпотентные консьюмеры, DLQ |
| Elasticsearch | Нечёткий поиск по каталогу | Анализаторы, синонимы, морфология |
| WebSocket | Дашборд склада | Масштабирование, переподключение, потерянные события |
| LLM + матрица совместимости | Подбор комплекта | Параллельный I/O, timeout, circuit breaker, fallback |
| Keycloak | Роли клиентов и персонала | OAuth2/OIDC, RBAC |
| Prometheus, Grafana, Loki, Jaeger | Поиск узких мест | Наблюдаемость под нагрузкой (k6/Gatling) |
| Оптимистичные блокировки (`@Version`) | Совместное редактирование карточек | Lost update |

### 1.5. Вне области (Out of Scope)

Юридические лица; доставка; несколько складов и городов; страхование через страховщика (заложено расширение `EXTERNAL_INSURANCE`); скрытые GPS-метки; квалифицированная электронная подпись; реальные интеграции с внешними провайдерами; промокоды и программа лояльности (кроме бонуса компенсации); мобильные приложения (только адаптивный веб).

## 2. Технологический стек и архитектурные принципы

### 2.1. Утверждённый стек `[РЕШЕНО]`

- **Ядро:** Java 17/21, Spring Boot 3, PostgreSQL + Liquibase.
- **События и CDC:** Apache Kafka + Debezium.
- **In-memory и кэш:** Redis (Redisson).
- **Поиск:** Elasticsearch.
- **Хранилище файлов:** MinIO (S3) — фото состояния «до/после», акты, договоры (PDF).
- **IAM:** Keycloak (OAuth2 / OIDC).
- **Observability:** Prometheus, Grafana, Loki, Jaeger (Micrometer Tracing).

### 2.2. Обязательные архитектурные принципы

1. **Каждый сервис владеет своей БД.** Прямых чтений чужих БД нет. Обмен — API и события.
2. **Transactional Outbox.** Любое доменное событие записывается в таблицу outbox в той же транзакции, что и изменение данных. Debezium читает outbox и публикует в Kafka. Двойная запись «БД + Kafka» запрещена.
3. **Идемпотентность.** Все консьюмеры и все команды с побочными эффектами (оплата, списание, бронирование) идемпотентны (idempotency key).
4. **Сага для распределённых операций** (оформление заказа, реаллокация). Рекомендация: оркестрация из Booking Service (прозрачнее для трассировки). Окончательный выбор — за архитекторами через ADR.
5. **Горячий путь бронирования не зависит синхронно от других сервисов.** Booking хранит локальную проекцию «обслуживаемые единицы по SKU/грейду», обновляемую событиями Inventory, и ежедневную сверку (reconciliation).
6. **Внешние системы — через порты** (адаптеры + заглушки), с таймаутами и circuit breaker.
7. **Конфигурируемость.** Все пороги и коэффициенты (`CFG`) — в конфигурации.
8. **Аудит-лог** всех смен статусов и денежных операций: кто, когда, почему, до/после. Неизменяемый.
9. **Единый источник правды по доступности — Booking Service.** Elasticsearch используется только для поиска по каталогу и не определяет доступность.

## 3. Роли, права и доступ

### 3.1. Принципы

1. Права выдаются **функциональным ролям**, а не должностям. Должность — это набор функциональных ролей (3.3). Пользователь может иметь любое число ролей одновременно, права суммируются.
2. Проверки выполняются по **разрешениям** вида `ресурс:действие` в каждом сервисе, а не только на Gateway. Проверок вида «если менеджер» в коде нет.
3. Реализация: Keycloak (realm roles + composite roles для должностей); сервисы проверяют разрешения из токена. Окончательная схема — за архитекторами (ADR).
4. Права клиента ограничены владением ресурса: только свои заказы, файлы, претензии.
5. Аудит-лог фиксирует пользователя, действие и **разрешение, давшее доступ** (`acted_under_permission`).
6. Совмещение ролей допустимо, но чувствительные действия защищены разделением обязанностей (3.4).
7. Выдача и изменение ролей выполняет только `ADMIN`, все изменения аудируются.
8. Сотрудник может одновременно быть клиентом (роль `CUSTOMER` + служебные роли). Конфликт интересов обрабатывается правилом 3.4 (п. 1).

### 3.2. Функциональные роли

| Роль | Основные разрешения |
|---|---|
| `CUSTOMER` | `catalog:read`, `cart:manage` (своя), `order:create/read/cancel/extend` (свои), `file:read` (свои), `claim:respond` (свои) |
| `CATALOG_EDITOR` | `sku:*`, `unit:create/update`, `kit:*`, `consumable:*`, `photo:upload` |
| `WAREHOUSE_OPERATOR` | `pickup-task:read/perform`, `handover:perform`, `return:accept`, `inspection:perform`, `defect:record`, `unit:scan` |
| `WAREHOUSE_SUPERVISOR` | `unit-assignment:override`, `unit-status:adjust` (с обязательной причиной), `escalation:handle` (просрочка инспекции, неявка), `checklist:manage` |
| `SERVICE_ENGINEER` | `maintenance:verdict`, `repair:manage`, `damage:assess`, `wear:reset` (после ТО), `unit:decommission:propose` |
| `RISK_MODERATOR` | `review:read/decide`, `customer-risk:read`, `blacklist:propose` |
| `SUPPORT_AGENT` | `order:read` (все), `customer:read`, `claim:manage`, `claim:resolve` (до порога), `refund:issue` (до порога), `notification:send-manual` |
| `FINANCE_OPERATOR` | `payment:read`, `charge:manual`, `debt:manage`, `writeoff:approve`, `fund-ledger:read`, `finance-report:read` |
| `PRICING_MANAGER` | `tariff:manage`, `pricing-config:manage`, `pricing-report:read` |
| `CONTENT_MANAGER` | `compat-rule:manage`, `search-dictionary:manage` |
| `AUDITOR` | `audit:read`, `report:read` (только чтение) |
| `ADMIN` | `user:manage`, `role:grant`, `config:manage` (технические `CFG`), `user:block/unblock`, `blacklist:approve`, `audit:read` |

### 3.3. Должности как наборы ролей (примеры, настраиваются в Keycloak)

| Должность | Функциональные роли |
|---|---|
| Кладовщик-универсал (типичная малая команда) | `WAREHOUSE_OPERATOR` + `WAREHOUSE_SUPERVISOR` + `RISK_MODERATOR` + `CATALOG_EDITOR` |
| Менеджер склада | `WAREHOUSE_OPERATOR` + `WAREHOUSE_SUPERVISOR` + `CATALOG_EDITOR` + `SUPPORT_AGENT` |
| Сервисный инженер | `SERVICE_ENGINEER` |
| Оператор поддержки | `SUPPORT_AGENT` + `RISK_MODERATOR` |
| Финансовый специалист | `FINANCE_OPERATOR` + `AUDITOR` |
| Владелец / руководитель | `ADMIN` + `PRICING_MANAGER` + `FINANCE_OPERATOR` + `AUDITOR` |

### 3.4. Разделение обязанностей (SoD)

| # | Чувствительное действие | Правило |
|---|---|---|
| 1 | Модерация, инспекция, разрешение претензии по **собственному заказу** сотрудника | Всегда `BLOCK` |
| 2 | Решение по претензии выше порога (`CFG` 20 000 ₽) | Утверждающий не тот, кто проводил инспекцию |
| 3 | Ручной возврат, прощение штрафа, ручное списание выше порога (`CFG` 10 000 ₽) | Второй утверждающий |
| 4 | Списание единицы (`DECOMMISSIONED`) и перевод в `LOST` | Второй утверждающий |
| 5 | Изменение тарифов и параметров цены | Только `PRICING_MANAGER`; действует с даты вступления, на уже зафиксированные цены не влияет |
| 6 | Ручная корректировка статуса единицы | Обязательная причина, аудит |
| 7 | Разблокировка клиента из чёрного списка | Решение `ADMIN` + согласование `SUPPORT_AGENT` |
| 8 | Выдача роли самому себе | Запрещена, требуется другой `ADMIN` |

**Режимы применения:** `BLOCK` (запрет), `SECOND_APPROVER` (нужен другой пользователь с нужным разрешением), `LOG_ONLY` (действие разрешено, помечается флагом и попадает в ежедневный отчёт).

**Режим по умолчанию** — `SECOND_APPROVER`. Если в системе меньше двух пользователей с нужным разрешением, действие автоматически переходит в `LOG_ONLY` с обязательным комментарием и алертом владельцу. Так малая команда, где всё делает один человек, не блокируется, но остаётся след для контроля. Пункт 1 всегда `BLOCK`.

Реализация согласования: события `ApprovalRequested` / `ApprovalGranted`, задачи в рабочем месте персонала.

### 3.5. Рабочее место персонала

Единый веб-интерфейс: разделы отображаются по разрешениям пользователя. Переключение «шапок» не требуется; дашборд склада показывает задачи по всем доступным пользователю функциям.

## 4. Глоссарий

| Термин | Определение |
|---|---|
| SKU | Модель оборудования (например, «Sennheiser MKE 600») |
| Единица (Unit) | Физический экземпляр с серийным номером |

| Холд | Заморозка средств на карте клиента (предавторизация) |
| План защиты (Protection Plan) | Платная опция, ограничивающая ответственность клиента за случайный ущерб суммой франшизы |
| Франшиза | Сумма, которую клиент платит при случайном ущербе при наличии плана защиты |
| Уровень доверия (Trust Level) | Внутренний рейтинг клиента L0–L3 по истории аренд |
| Грейс-период | Окно возврата без штрафа (2 ч) |
| Функциональная роль | Набор разрешений на группу действий (например, `WAREHOUSE_OPERATOR`). Выдаётся пользователю независимо от должности |
| Должность | Набор функциональных ролей конкретного сотрудника |
| SoD (разделение обязанностей) | Политика, не позволяющая одному человеку единолично выполнить и утвердить чувствительное действие |
| Стоимость замещения | Рыночная цена новой сопоставимой единицы (уровень SKU); основа для TAV, франшизы и претензий по утрате |
| Балансовая (остаточная) стоимость | Первоначальная стоимость единицы минус накопленная амортизация (управленческий учёт) |
| Амортизация по выработке | Списание стоимости единицы пропорционально износу в днях (Wear Days) |
| Фонд обновления парка (F1) | Накопления на закупку замены изношенной техники |
| Резерв ремонта и ТО (F2) | Накопления на ремонт и техобслуживание |
| Резерв убытков (F3) | Накопления на покрытие ущерба, утрат и споров за счёт платформы |
| Экономический пол цены | Минимальная цена суток, не покрывающая ниже амортизацию и резерв ремонта с маржой |

## 5. Бизнес-правила

### 5.1. Каталог и учёт оборудования

1. Каталог: SKU → единицы (серийные) + расходники (количественные) + комплекты. `[РЕШЕНО]` как часть модели (расходники и комплекты — `[ПРЕДЛОЖЕНИЕ]`).
2. Бронирование выполняется на уровне **SKU и грейда**, не серийного номера.
3. Серийный номер назначается заказу **за 24 часа до выдачи** фоновым заданием (или вручную кладовщиком при сборке).
4. Правило выбора единицы при назначении (`CFG`): предпочитать единицу с наименьшим `total_wear_days` внутри нужного грейда.
5. Расходники не бронируются по серийным номерам: учитывается количество, выдача и возврат по счётчику, недостача фиксируется в акте.
6. После возврата носителей данных (карты памяти, SSD) обязательна процедура очистки, отражённая в чек-листе.
7. Комплект содержит перечень позиций и обязательных аксессуаров. Бронирование комплекта резервирует ёмкость каждой позиции; неполный комплект не выдаётся.

### 5.2. Бронирование и ёмкость

| Правило | Значение |
|---|---|
| Определение суток | Суточная аренда = 24 часа от начала слота выдачи. Срок возврата — то же время суток через N суток |
| Режим работы пункта | `CFG` 09:00–21:00 MSK; слоты выдачи и возврата по 1 часу; пропускная способность слота `CFG` |
| Возврат вне часов работы | Невозможен (постамат вне области). Срок возврата выбирается только в часы работы |
| Единица планирования ёмкости | Календарный день, посуточные «корзины» (SKU × грейд × день) |
| Занятость | С даты выдачи по дату возврата включительно. Для SKU с флагом `same_day_turnaround=true` день возврата свободен для повторной выдачи |
| Формула | `capacity(SKU, грейд, день) = обслуживаемые единицы − забронировано` |
| Корзина (`DRAFT`) | **Не резервирует ёмкость.** Показывает доступность информативно |
| Начало оформления | Резервирует ёмкость с TTL `CFG` = 15 минут (статус `PENDING_PAYMENT`). По истечении — `EXPIRED`, ёмкость возвращается |
| Фиксация цены | Цена фиксируется на момент начала оформления (price snapshot) и действует в пределах TTL |
| Обслуживаемые единицы | Единицы не в статусах `IN_REPAIR`, `MAINTENANCE`, `DECOMMISSIONED`, `LOST`. Их изменение пересчитывает ёмкость |
| Неявка (no-show) | Бронь удерживается `CFG` 2 часа от начала слота. Затем заказ → `NO_SHOW`, ёмкость освобождается |

**Требование к реализации `[РЕШЕНО]`:** бронирование не допускает овербукинга при конкурентных запросах. Критерий приёмки: 200 параллельных запросов на последнюю единицу дают ровно один успех.

### 5.3. Ценообразование

Расчёт выполняет Booking & Pricing Service.

#### 5.3.1. Структура итоговой цены заказа

| Компонент | Что это | В итоговой сумме к оплате | Примечание |
|---|---|---|---|
| Аренда | Сумма дневных цен по позициям | Да | 5.3.2 |
| Защита аренды | Плата за план защиты | Да | 5.3.4 |
| Холд | Заморозка средств на карте | Нет (не выручка, возвращается) | Показывается отдельно: «будет заморожено» |
| Штрафы и сборы | Просрочка, отмена, неявка | Нет; возникают по событиям | 5.7, 5.10 |
| Бонусный кредит | Компенсация при овербукинге | Способ оплаты (уменьшает сумму к оплате, не скидка) | 5.8 |

До оплаты клиент видит: цену по дням, применённые скидки и наценки, строку защиты, итог к оплате, сумму холда, условия отмены, размер франшизы. Итоговая сумма к оплате для физлица — окончательная (налоги входят в цену, Q24).

#### 5.3.2. Расчёт стоимости аренды позиции

`цена_дня(d) = базовая_ставка(SKU) × коэф_длительности(N) × (1 − скидка_грейда) × (1 + наценка_спроса(d))`

`стоимость_позиции = Σ по дням цена_дня(d) × количество`

Округление до копеек — только у итоговой цены дня.

| Компонент | Правило |
|---|---|
| Базовая ставка | За сутки на SKU, версионируется тарифом (5.3.6) |
| Коэффициент длительности `[ПРЕДЛОЖЕНИЕ]` | Применяется ко всем дням аренды. Пример `CFG`: 1 сутки 1.00; 2–3 сут 0.90; 4–7 сут 0.80; 8–14 сут 0.70; свыше 14 сут 0.65. Может отличаться по категориям |
| Скидка грейда | Грейд B: 15% `CFG` |
| Наценка спроса | +30% `CFG` для каждого дня, когда загрузка категории превышает 80% `CFG`. Загрузка дня = (подтверждённые и зарезервированные брони категории) / (ёмкость категории) на момент начала оформления, без учёта текущего заказа. SKU может переопределить расчёт. Возможны ступени как расширение |
| Продление | Наценка спроса не применяется. Добавленные дни считаются по коэффициенту длительности для **нового общего срока**; оплаченные дни назад не пересчитываются `[ПРЕДЛОЖЕНИЕ]` |
| Пол цены | Цена дня не ниже экономического пола SKU (5.12.5). При срабатывании заказ получает флаг `PRICE_FLOOR_APPLIED` |
| Потолок цены | Эффективный множитель не выше 1.5 от базовой ставки `CFG` (защита от «шоковых» цен) |
| Порядок | Расчёт → применение пола → применение потолка |

#### 5.3.3. Пример расчёта (иллюстративный)

Камера: базовая ставка 3 000 ₽/сут, грейд B, аренда 5 суток (коэффициент 0.80), на третий день загрузка категории >80%. TAV 300 000 ₽ (средний уровень риска).

| Позиция расчёта | Значение |
|---|---|
| Обычный день: 3 000 × 0.80 × 0.85 × 1.00 | 2 040,00 ₽ |
| День с наценкой: 3 000 × 0.80 × 0.85 × 1.30 | 2 652,00 ₽ |
| Аренда: 4 × 2 040 + 2 652 | 10 812,00 ₽ |
| Защита: 7% от аренды | 756,84 ₽ |
| **Итого к оплате** | **11 568,84 ₽** |
| Холд (10% TAV, отдельно) | 30 000,00 ₽ |

Проверка пола (пример 5.12): 2 040 ₽ выше экономического пола 648 ₽, пол не применяется.

#### 5.3.4. Защита аренды в цене

- Плата за план = `fee_percent` × стоимость аренды (без холда и штрафов); по умолчанию 7% (диапазон 5–10%), настраивается по категориям.
- Плата входит в итоговую сумму к оплате и показывается **отдельной строкой** до оплаты (прозрачность; юридическая форма плана не определена, Q22).
- **Низкий уровень риска:** план предлагается, клиент подтверждает явным действием (без предустановленного согласия, требуется проверка юристом). При отказе — повышенный холд (`CFG` 10 000 ₽) и полная ответственность за ущерб.
- **Средний и высокий уровни:** план обязателен и входит в цену как часть условий аренды, отказаться нельзя.
- **Fallback** (`protection_plan.enabled = false`): строка защиты отсутствует, применяется повышенная шкала холда: низкий 10 000 ₽; средний 15% TAV; высокий 20% TAV `CFG`.
- При продлении плата начисляется пропорционально добавленной стоимости аренды. Возврат платы — по правилам 5.5.3.
- Сборы за защиту поступают в резерв убытков (5.12.4).

#### 5.3.5. Фиксация цены в заказе (price snapshot)

Хранятся: версия тарифа, ставка, коэффициент длительности, грейд, наценка по дням, плата за защиту, TAV, сумма холда, флаги пола и потолка, время фиксации и TTL. Пересчёт после подтверждения заказа запрещён, допускаются только продление, отмена и штрафы.

#### 5.3.6. Управление тарифами

- Тариф — версионируемая сущность: ставка, коэффициенты, `fee_percent`, пол и потолок. Вступает в силу с указанной даты; действующие брони сохраняют зафиксированные цены.
- Изменения вносит `PRICING_MANAGER`, они аудируются и публикуют событие `TariffChanged`.
- Симулятор цены: расчёт для SKU и дат с полной раскладкой (для менеджера и поддержки).
- Аналитика для настройки ставок (утилизация, экономический пол, рекомендованная ставка, окупаемость, 5.12.5). В MVP рекомендации только показываются, автоматически не применяются.

#### 5.3.7. Штрафы и сборы

Штрафы (5.7, 5.10) не входят в цену аренды. **Суточная стоимость позиции для штрафа** = стоимость позиции по заказу / число суток, без платы за защиту (уточняет формулировку «50% суточной стоимости»).

### 5.4. Износ и цифровой паспорт (Smart Depreciation)

Метрики паспорта единицы:

- `total_wear_days` — накопленный износ за всё время (никогда не обнуляется, кроме решения инженера при капитальном восстановлении).
- `service_wear_days` — износ с последнего ТО (обнуляется вердиктом инженера).

**Начисление** при завершении аренды (после возврата):

- База: фактические дни использования (от выдачи до возврата), округление вверх до целых суток, минимум 1.
- Длительная аренда: если фактический срок >7 суток `CFG`, применяется коэффициент ×1.2 `CFG` ко **всем** дням этой аренды.
- Начисление идемпотентно, привязано к идентификатору заказа. При отмене или пересмотре ущерба возможна корректировка (событие `WearAdjusted`).

**Пороги** (`CFG`, могут отличаться по категориям):

| Порог | Действие |
|---|---|
| `total_wear_days` ≥ 50 | Единица получает тег `COSMETIC_WEAR` и переходит в пул **грейда B**. Скидка 15% |
| `service_wear_days` ≥ 100 | После возврата статус принудительно `MAINTENANCE` (обязательное ТО); дальнейшая сдача заблокирована до вердикта инженера |

**Смена грейда при уже сделанных бронях:** переход A → B уменьшает пул A. Если ёмкость пула A стала меньше числа броней, срабатывает процедура овербукинга (5.8). Переход B → A невозможен.

### 5.5. Риски, KYC и «Защита аренды»

#### 5.5.1. Уровень риска заказа

Уровень определяется как **максимум** из уровня по TAV и уровня по сроку. Границы не пересекаются (в v2 «до 3 дней» и «от 3 до 14» пересекались).

| Уровень | Условия | Проверки | Обеспечение |
|---|---|---|---|
| **Низкий** | TAV ≤ 100 000 ₽ и срок ≤ 3 сут | Банковский ID (порт `IdentityProvider`), электронное согласие с офертой | План защиты (5–10% от стоимости аренды `CFG`, входит в итоговую цену, см. 5.3.4) или повышенный холд при отказе от плана; холд до 5 000 ₽ `CFG` |
| **Средний** | TAV 100 000–500 000 ₽ или срок 4–14 сут | ЕСИА (порт), очная проверка паспорта при выдаче, договор материальной ответственности через ПЭП (SMS) | План защиты **обязателен** + холд до 10% TAV `CFG` |
| **Высокий** | TAV > 500 000 ₽ или срок > 14 сут | ЕСИА + `RiskCheckProvider` (БКИ, сейчас заглушка) + **ручная модерация** (звонок менеджера, уточнение локации съёмок) + очное подписание бумажного договора на пункте выдачи | План защиты обязателен + холд 10–20% TAV `CFG` |

Дополнительно:

- Высокий уровень доступен клиентам с уровнем доверия ≥ L2. Иначе — только по решению менеджера.
- КЭП и скрытые GPS-метки исключены `[РЕШЕНО]`.
- Сканы паспортов **не хранятся**: сохраняется только факт и результат проверки (принцип минимизации данных). Фото состояния техники и акты хранятся в MinIO.

#### 5.5.2. Слои защиты

| # | Слой | Описание |
|---|---|---|
| 1 | Договорная ответственность | Договор-оферта с материальной ответственностью; подтверждение ПЭП |
| 2 | Финансовое обеспечение | Холд. Если срок аренды больше допустимого срока жизни холда (`CFG` 7 сут), вместо долгого холда — привязка карты с согласием на списание в договоре и периодическая переавторизация |
| 3 | План защиты | См. 5.5.3 |
| 4 | Идентификация | ЕСИА или банковский ID плюс очная проверка при выдаче |
| 5 | Доказательная база | Фото «до/после», акт приёма-передачи, чек-лист комплектации, подпись клиента |
| 6 | Прогрессивные лимиты доверия | См. 5.5.4 |
| 7 | Взыскание | Порядок: холд → токенизированная карта → досудебная претензия по шаблону. Дальнейшее (суд, коллекторы) вне системы |
| 8 | Резерв на убытки | Часть сборов за защиту учитывается в резерве; метрика loss ratio для настройки процентов |

**Fallback до юридического решения:** слои 1, 2, 4, 5, 6, 7 работают всегда. Слой 3 включается флагом `protection_plan.enabled`. Пока юридическая форма не утверждена, план защиты в документах не называется страхованием.

#### 5.5.3. План защиты (Protection Plan)

Сущность с полями: `type` (`INTERNAL_WAIVER` | `EXTERNAL_INSURANCE` — зарезервирован), `fee_percent`, `franchise`, `coverage_matrix`, `limit`.

| Риск | Покрытие |
|---|---|
| Случайное механическое повреждение | Клиент отвечает в размере франшизы, остальное — за счёт платформы |
| Умысел, грубая небрежность, нарушение условий эксплуатации | Не покрывается (полная ответственность) |
| Утрата, кража | Не покрывается (полная стоимость замещения) `[ПРЕДЛОЖЕНИЕ]` |
| Залитие, пыль/песок | Не покрывается `[ПРЕДЛОЖЕНИЕ]` |
| Расходники и аксессуары без серийного номера | Не покрывается |

Франшиза `CFG`: 10% стоимости замещения повреждённой позиции, минимум 3 000 ₽ `[ПРЕДЛОЖЕНИЕ]`. Матрица покрытия настраивается по категориям.

Плата за план: возвращается при отмене до выдачи, не возвращается после выдачи.

#### 5.5.4. Уровни доверия

| Уровень | Условие | Максимум TAV | Одновременных заказов |
|---|---|---|---|
| L0 (новый) | Нет истории | 100 000 ₽ | 1 |
| L1 | ≥ 2 «чистые» аренды | 300 000 ₽ | 2 |
| L2 | ≥ 5 | 500 000 ₽ | 3 |
| L3 | ≥ 10 и без споров по вине клиента за 12 мес | без лимита (проверки высокого уровня сохраняются) | 5 |

Все значения — `CFG`. «Чистая аренда» — завершена без просрочки сверх грейс-периода и без `DISPUTED` по вине клиента.

Нарушения: ущерб по вине клиента или неоплата → снижение до L0 на 6 мес `CFG`. Утрата или невозврат → чёрный список и блокировка учётной записи в Keycloak.

### 5.6. Выдача, возврат и инспекция

**Выдача (очная):**

1. Клиент называет заказ, кладовщик открывает задачу сборки.
2. Кладовщик сканирует серийные номера единиц (QR/штрихкод) и сверяет с назначением.
3. Проверка личности: сверка документа с данными профиля из провайдера идентификации. Фиксируется результат проверки (без хранения скана).
4. Оформляется **акт приёма-передачи**: список единиц, комплектация, фото состояния «до», подпись клиента (подтверждение в приложении или ПЭП). Для высокого уровня — бумажный договор.
5. Единицы → `IN_USE`, заказ → `ACTIVE`.

**Возврат:**

1. Кладовщик принимает технику, сверяет комплектацию, делает фото «после».
2. Единицы → `RETURNED_PENDING_INSPECTION`. Клиент подписывает акт возврата (фиксирует состояние на момент возврата).
3. Инспекция: осмотр и проверка работоспособности; решение: `OK` → `MAINTENANCE` (чистка) → `AVAILABLE`, либо дефект → открывается претензия (5.9).

**SLA инспекции `[ПРЕДЛОЖЕНИЕ]` (заменяет автопереход в `AVAILABLE` из v2):**

- Инспекция должна завершиться за 4 рабочих часа `CFG`. Рабочие часы определяются календарём пункта выдачи (выходные, праздники).
- При нарушении срока: событие эскалации дежурному менеджеру, метка `INSPECTION_OVERDUE`. **Единица остаётся вне аренды**, автоперехода в `AVAILABLE` нет.
- Ответственность клиента: холд снимается после завершения инспекции либо не позднее чем через 72 часа `CFG` после возврата. Претензия по скрытым дефектам после снятия холда возможна в течение `CFG` 3 суток на основании акта возврата и фото.

### 5.7. Просрочка возврата и биллинг

| Опоздание | Действие |
|---|---|
| ≤ 2 ч | Грейс-период, без штрафа |
| 2–12 ч | Штраф 50% суточной стоимости (по позиции, см. 5.3.7) |
| > 12 ч `[ПРЕДЛОЖЕНИЕ]` | Полные сутки за каждые начатые сутки просрочки, заказ → `OVERDUE`; через 24 ч — звонок и досудебная претензия; через 72 ч `CFG` — менеджер решает о переводе единицы в `LOST` |

**Каскад просрочки:** при просрочке сверх грейса система проверяет ближайшую бронь на ту же SKU/грейд. Если выдача ближе `CFG` 12 часов, запускается процедура овербукинга (5.8) для брони под угрозой.

**Порядок списания штрафа (Graceful Degradation):**

1. Списание с токенизированной карты.
2. При ошибке — списание из холда.
3. При нехватке — событие в Notification Service (SMS/email о долге), запись долга `DEBT` в заказ, перевод заказа в `DISPUTED` для ручной обработки.

Расчёт выполняют планировщик с защитой от двойного запуска и outbox. Kafka как таймер не используется.

### 5.8. Овербукинг и реаллокация

Овербукинг возникает, когда ёмкость SKU/грейда стала меньше числа броней (поломка, `MAINTENANCE`, смена грейда, просрочка предыдущего клиента).

**Кого вытесняем `[РЕШЕНО]`:** бронь, оформленную последней (LIFO по времени подтверждения). Исключение: клиенты с более высоким уровнем доверия вытесняются в последнюю очередь.

**Лестница предложений клиенту (шаг применяется, если предыдущий невозможен):**

1. Идентичная модель из другого пула (в том числе B → A) **без доплаты**.
2. **Апгрейд** на модель выше классом: бесплатно, если разница цены ≤ `CFG` порога X; иначе с доплатой за разницу. Клиент вправе отказаться.
3. Совместимый аналог другого бренда (по матрице совместимости) с согласием клиента.
4. Отмена с возвратом 100% + **компенсация**.

**Компенсация `[РЕШЕНО]` (вариант «б»):** возврат 100% уплаченных сумм (включая план защиты) + бонус в виде кредита на следующую аренду: 15% `CFG` от стоимости заказа, минимум фиксированной суммы `CFG`, срок действия 90 суток `CFG`. Возмещение косвенных расходов клиента (студия, съёмочная группа) не предусмотрено; ответственность ограничена в оферте.

**Процесс:**

- Клиент получает уведомление сразу; срок решения `CFG` 6 часов, но не позднее чем за 4 часа до слота выдачи.
- Если клиент не ответил — применяется вариант без доплаты по лестнице (шаги 1, затем 2 при нулевой доплате). Если такого нет — шаг 4.
- Все решения фиксируются в аудит-логе. Заказ сохраняет связь «исходная позиция → замена».

### 5.9. Споры и ущерб

1. При обнаружении дефекта позиция → `DAMAGED`, заказ → `DISPUTED`. Кладовщик фиксирует дефект и фото.
2. Инженер оценивает: стоимость ремонта либо стоимость замещения с учётом износа.
3. Размер претензии = оценка − покрытие плана защиты (или франшиза при случайном ущербе).
4. Клиент уведомляется и имеет `CFG` 3 суток на ответ через веб-интерфейс.
5. Удержание из холда в пределах претензии; остаток холда возвращается. Если претензия превышает холд — списание с токенизированной карты, затем досудебная претензия.
6. Решение фиксирует менеджер поддержки (роль, дата, обоснование). SLA рассмотрения `CFG` 5 рабочих дней.
7. Судебное урегулирование вне системы.

### 5.10. Отмена, перенос, возврат средств `[ПРЕДЛОЖЕНИЕ]`

| Ситуация | Правило (`CFG`) |
|---|---|
| Отмена ≥ 24 ч до выдачи | Полный возврат, включая план защиты |
| Отмена < 24 ч до выдачи | Штраф 20% стоимости аренды; план защиты возвращается |
| Неявка | Заказ → `NO_SHOW`; удержание 50% стоимости первых суток; остальное возвращается |
| Перенос дат | Один бесплатный перенос при наличии ёмкости; повторный — как отмена + новое бронирование |
| Досрочный возврат | Пересчёт не производится; износ считается по фактическим дням |

### 5.11. Статусные модели

**Единица оборудования (Inventory).** Статус `BOOKED` из прежних версий заменён на `ASSIGNED`, так как бронь делается на SKU, а единица привязывается позже.

| Статус | Описание | Вход | Выход |
|---|---|---|---|
| `AVAILABLE` | Готова к аренде | После ТО/инспекции; новая единица | → `ASSIGNED`, `IN_REPAIR`, `DECOMMISSIONED` |
| `ASSIGNED` | Назначена заказу за 24 ч до выдачи | Задание назначения / кладовщик | → `IN_USE`, `AVAILABLE` (отмена, неявка) |
| `IN_USE` | У клиента | Очная выдача | → `RETURNED_PENDING_INSPECTION`, `LOST` |
| `RETURNED_PENDING_INSPECTION` | Ждёт инспекции | Приём возврата | → `MAINTENANCE`, `IN_REPAIR` |
| `MAINTENANCE` | Чистка/ТО | После инспекции; износ ≥ порога | → `AVAILABLE`, `IN_REPAIR` |
| `IN_REPAIR` | Ремонт | Инженер | → `AVAILABLE`, `DECOMMISSIONED` |
| `DECOMMISSIONED` | Списана | Менеджер/инженер | — |
| `LOST` | Утрачена | Менеджер | → `DECOMMISSIONED` |

**Заказ (Order):**

| Статус | Описание |
|---|---|
| `DRAFT` | Корзина, ёмкость не держит |
| `PENDING_PAYMENT` | Ёмкость зарезервирована с TTL, идёт оплата/холд/риск-проверка |
| `PENDING_REVIEW` | Только высокий риск: ожидание модерации (ёмкость держится) |
| `RESERVED` | Подтверждён, ждёт выдачи |
| `ACTIVE` | Выдан |
| `OVERDUE` | Просрочен возврат |
| `RETURNED` | Возвращён, ждёт инспекции |
| `COMPLETED` | Закрыт без претензий |
| `DISPUTED` | Спор по дефекту или неоплата |
| `CANCELLED` | Отменён |
| `EXPIRED` | Истёк TTL оформления |
| `NO_SHOW` | Клиент не явился |

**Позиция заказа (Order Line)** нужна для частичных возвратов и споров: `RESERVED` → `ASSIGNED` → `ISSUED` → `RETURNED` → `INSPECTED_OK` | `DAMAGED` | `LOST`. Статус заказа выводится из статусов позиций по правилам, которые описывают архитекторы.

Матрица переходов, инициаторы и обработка недопустимых переходов фиксируются в спецификации сервисов. Все переходы пишутся в аудит-лог.

### 5.12. Управленческий учёт парка: амортизация и фонды `[ПРЕДЛОЖЕНИЕ]`

В v3.0 рассчитывался только **износ в днях** (Wear Days): операционная метрика для грейдов и ТО. Денежная амортизация и отчисления в фонды не считались. Этот раздел добавляет управленческий учёт: часть выручки автоматически откладывается на обновление парка, ремонт и убытки, по аналогии с резервом отпусков при расчёте зарплаты.

#### 5.12.1. Принципы

- Это **управленческий**, а не бухгалтерский или налоговый учёт. Он не заменяет бухгалтерскую амортизацию; данные можно выгрузить бухгалтеру. Налоговый режим и бухгалтерские правила вне области (Q24).
- Начисления — записи в журнале (ledger), а не движение денег. Фактические траты списываются с фондов.
- Расчёт автоматический, по событиям, идемпотентный, журнал только на добавление (append-only).
- Отрицательный остаток фонда не блокирует операции, а генерирует алерт.

#### 5.12.2. Две разные оценки стоимости

| Оценка | Уровень | Назначение |
|---|---|---|
| Стоимость замещения (`replacement_value`) | SKU | TAV, франшиза, претензии по утрате. Обновляется вручную раз в `CFG` квартал |
| Первоначальная стоимость (`acquisition_cost`) → балансовая (`book_value`) | Единица | Амортизация, отчёты, результат выбытия |

#### 5.12.3. Амортизация по выработке

Поля цифрового паспорта: `acquisition_cost`, `acquisition_date`, `residual_value_percent` (`CFG` по категориям, стартово 30%), `expected_life_wear_days` (`CFG` по категориям), `accumulated_amortization`, `book_value`.

`амортизация_за_Wear_Day = acquisition_cost × (1 − residual_value_percent) / expected_life_wear_days`

При каждом начислении износа (событие `WearUpdated`) начисляется `Δwear_days × амортизация_за_Wear_Day`. Повышающий коэффициент длительной аренды ×1.2 автоматически увеличивает начисление: техника изнашивается быстрее.

**Календарный минимум (устаревание простоя) `[ПРЕДЛОЖЕНИЕ]`:** при ежемесячном закрытии, если начисление по выработке за месяц меньше линейной нормы `acquisition_cost × (1 − residual) / срок_в_месяцах` (`CFG` 60 мес), доначисляется разница. Накопленная амортизация не превышает `acquisition_cost × (1 − residual)`.

**Пример:** стоимость 300 000 ₽, остаточная 30%, срок 500 Wear Days: 300 000 × 0.7 / 500 = **420 ₽ за Wear Day**. Аренда 5 суток даёт 2 100 ₽ амортизации. Аренда 10 суток даёт 12 Wear Days (×1.2) и 5 040 ₽.

#### 5.12.4. Фонды

| Фонд | Назначение | Начисление | Списание |
|---|---|---|---|
| F1. Обновление парка | Закупка замены изношенной техники | Амортизация по выработке + календарный минимум | Закупка новых единиц; остаточная стоимость при выбытии |
| F2. Ремонт и ТО | Ремонт и техобслуживание | `repair_rate_per_wear_day × Δwear_days` (`CFG` по категориям; стартово около 4% базовой ставки, далее калибруется по фактическим расходам) | Фактические затраты (`RepairCompleted`) |
| F3. Убытки | Доля платформы при ущербе, утрате, спорах | Доля `loss_reserve_share` (`CFG`, стартово 100%) от сборов за защиту, плюс штрафы и удержания | Выплаты по претензиям за счёт платформы (за вычетом франшизы клиента), списание утраченных единиц |

**Выбытие единицы** (`DECOMMISSIONED`, `LOST`): остаточная балансовая стоимость списывается; фиксируется результат выбытия = поступления (взыскание с клиента, продажа остатка) − балансовая стоимость.

#### 5.12.5. Экономический пол, рекомендованная ставка, окупаемость

- `экономический_пол_дня = (амортизация_за_Wear_Day + repair_rate_per_wear_day) × (1 + floor_margin)`, `floor_margin` `CFG` 20%. Пример: (420 + 120) × 1.2 = **648 ₽**.
- `рекомендованная_ставка = (амортизация_за_Wear_Day + repair_rate_per_wear_day + накладные_на_день_аренды) × (1 + целевая_маржа)`. Накладные на день аренды и целевая маржа задаются финансистом (`CFG`). В MVP значение только рекомендуется.
- **Срок окупаемости единицы** = `acquisition_cost` / (средняя месячная выручка единицы − переменные затраты).

#### 5.12.6. Отчёты

Остатки фондов по SKU, категории, парку; накопленная амортизация и балансовая стоимость; утилизация и выручка на единицу; окупаемость; loss ratio; маржа после фондов. Доступ: `FINANCE_OPERATOR`, `AUDITOR`, `ADMIN`. Ежемесячное закрытие периода выполняет планировщик.

## 6. Функциональные требования к сервисам

Границы сервисов — рекомендация; окончательное решение фиксируется в ADR.

### 6.1. API Gateway и Identity

- Единая точка входа, проверка JWT, rate limiting, генерация Trace ID для каждого запроса.
- Keycloak: функциональные роли и составные роли-должности (раздел 3), совмещение ролей одним пользователем, блокировка учётной записи при нарушениях (утрата, невозврат, чёрный список).
- Проверка разрешений выполняется в каждом сервисе. Политики SoD (3.4) реализуются через согласования (`ApprovalRequested` / `ApprovalGranted`).
- Гость может просматривать каталог; оформление заказа требует авторизации.

### 6.2. Booking & Pricing Service (ядро транзакций)

Объединён, так как цена зависит от загрузки категории.

- Расчёт ёмкости, бронирование, TTL-резервы, фиксация цены, расчёт цены (5.2, 5.3).
- Управление тарифами: версионирование, вступление в силу с даты, симулятор цены, аудит (5.3.6).
- Оркестрация саги оформления (`CapacityReserved` → `RiskAssessed` → `PaymentAuthorized` → [`ReviewApproved`] → `OrderConfirmed`). Компенсации: освобождение ёмкости, снятие холда.
- Управление заказами и позициями, статусами, продлением, отменами (5.10).
- Овербукинг: обнаружение, лестница, уведомления, компенсация (5.8).
- Планировщик: истечение TTL, no-show, назначение единиц за 24 часа, расчёт просрочек.
- Локальная проекция обслуживаемых единиц по SKU/грейду (события Inventory) + ежедневная сверка.
- API доступности: пакетный запрос доступности для списка SKU/дат (для каталога и AI), с коротким кэшем (Redis).
- **Технологическое требование:** выбор стратегии конкурентного доступа к счётчику ёмкости (пессимистичная блокировка, оптимистичная блокировка, распределённый лок Redisson) обосновывается ADR и подтверждается нагрузочным тестом.

### 6.3. Inventory Service (склад)

- Карточки SKU, единицы, комплекты, расходники, цифровой паспорт, статусы (5.1, 5.4, 5.11).
- Складские операции: задачи сборки, акты выдачи и возврата, чек-листы, инспекции, претензии по дефектам (5.6, 5.9). `[ПРЕДЛОЖЕНИЕ]` по границе сервиса.
- Начисление износа, смена грейда, принудительное ТО.
- Финансовые атрибуты цифрового паспорта: первоначальная стоимость, остаточная стоимость, срок в Wear Days, накопленная амортизация (5.12.3). Источник данных для Finance & Analytics.
- Оптимистичные блокировки (`@Version` в JPA) на карточках; одновременное редактирование двумя менеджерами не приводит к потере правок.
- Фото и акты — в MinIO; доступ к ним по pre-signed URL с коротким TTL (`CFG` 5 минут), права по ролям.
- Публикует события изменения обслуживаемых единиц (`ServiceableUnitsChanged`) для Booking.

### 6.4. Payments Service

Отсутствовал в v1 и v2.

- Холд (предавторизация), захват, снятие, списание с токенизированной карты, возвраты, переавторизация длинных холдов.
- Идемпотентные операции, статусы платёжных операций, сверка с провайдером.
- Порядок списания штрафов (5.7).
- Порт `PaymentGateway` и `FiscalizationGateway` — заглушки (раздел 8).
- В системе не хранятся номера карт; только токены.

### 6.5. Risk & Trust Service

- Определение уровня риска заказа (5.5.1), уровней доверия (5.5.4), проверка лимитов.
- Оркестрация проверок через порты `IdentityProvider`, `RiskCheckProvider`.
- Очередь модерации для высокого уровня (задача модератору, SLA `CFG` 2 рабочих часа, исход: одобрен / отклонён с причиной).
- Чёрный список, история нарушений, событие блокировки для Keycloak.

### 6.6. Notification & Live Service

- Каналы: SMS, email, веб-уведомления. Telegram — расширение на будущее.
- Дашборд склада на WebSocket: новые заказы, задачи сборки, эскалации.
- Требования: durable-состояние в БД (сокет — только доставка), восстановление пропущенных событий после переподключения, горизонтальное масштабирование.
- Уведомление клиента о статусе заказа, овербукинге, просрочке, долге, претензии.

### 6.7. AI-Assistant & Compatibility Service

- Перевод запроса («нужен звук для подкаста на двоих») в корзину.
- Конвейер:
  1. Запрос в LLM (порт `LlmProvider`): намерения и категории.
  2. **Матрица совместимости** (обязательный шаг): проверка байонетов, питания, кабелей, синхронизации по реляционной или графовой модели правил.
  3. Параллельно (виртуальные потоки / `CompletableFuture`): поиск в каталоге и запрос доступности в Booking.
- Несовместимые позиции заменяются валидными аналогами, **а клиент видит объяснение замены** («заменили X на Y, потому что…»). Замена не должна приводить к недоступной или заметно более дорогой позиции без пометки.
- Данные матрицы ведёт специалист по контенту (роль); нужен интерфейс управления и версионирование правил.
- Ограничения и защита: таймаут `CFG` 8 сек, circuit breaker, fallback на подбор по ключевым правилам категорий; защита от prompt injection; ограничение размера корзины; персональные данные в LLM не передаются (обезличивание).
- Метрики: latency, доля принятых подборок, доля замен матрицей, стоимость запросов.

### 6.8. Search & CDC Pipeline

- Debezium читает WAL PostgreSQL (таблицы outbox и каталога), события идут в Kafka; Search Consumer обновляет индекс Elasticsearch.
- Нечёткий поиск по-русски и латиницей («синхайзер» → Sennheiser): морфология, транслитерация, словарь синонимов, обработка опечаток.
- Elasticsearch **не определяет доступность**. Выдача поиска обогащается флагом доступности через пакетный запрос к Booking.
- Консьюмер идемпотентен; DLQ для «ядовитых» сообщений; лаг индексации мониторится.
- История ремонтов и аналитика — по событиям Inventory.

### 6.9. Finance & Analytics Service

Событийная проекция без влияния на горячий путь бронирования. `[ПРЕДЛОЖЕНИЕ]` по границе (может быть модулем Inventory; рекомендация — отдельный сервис ради учебной ценности event-driven проекции).

- Подписывается на события (`WearUpdated`, `OrderCompleted`, `RepairCompleted`, `ClaimResolved`, `UnitAcquired`, `UnitDecommissioned`) и ведёт журнал начислений и списаний по фондам F1–F3 (5.12.4).
- Журнал append-only, идемпотентность по `event_id`, возможность полного пересчёта из событий (replay).
- Изменение ставок и параметров действует вперёд, исторические записи не меняются.
- Расчёт балансовой стоимости, календарного минимума, ежемесячного закрытия периода.
- Отчёты и дашборды (5.12.6); экспорт данных для бухгалтера.
- Хранит собственную БД журнала; атрибуты единиц получает из событий Inventory.

## 8. Внешние интеграции (порты и заглушки)

| Порт | Назначение | Реализация в проекте | Будущее |

| `IdentityProvider` | Банковский ID / ЕСИА | Заглушка с тестовыми профилями | Реальный провайдер |
| `RiskCheckProvider` | БКИ, скоринг | NoOp (всегда «пройдено») + настраиваемые тестовые сценарии | БКИ при необходимости |
| `PaymentGateway` | Холд, списания, возвраты | Имитация банка (сценарии: успех, отказ, нехватка средств, таймаут) | Российский эквайринг |
| `FiscalizationGateway` | Онлайн-чеки | Заглушка | Провайдер фискализации |
| `SmsGateway` / `EmailGateway` | Уведомления, ПЭП | Заглушка, логирование | SMS-провайдер |
| `LlmProvider` | AI-подбор | Реальный или мок-LLM с детерминированными ответами для тестов | Российский провайдер |

Все порты: таймауты, ретраи, circuit breaker, метрики, трассировка. Заглушки поддерживают сценарии отказа для тестов устойчивости.

## 9. Нефункциональные требования

### 9.1. Производительность и устойчивость (целевые значения для нагрузочных тестов `[ПРЕДЛОЖЕНИЕ]`)

| Показатель | Цель |
|---|---|
| Поиск по каталогу | p95 < 200 мс при 150 RPS |
| Запрос доступности (пакетный) | p95 < 300 мс |
| Бронирование (без внешних вызовов) | p95 < 500 мс при 15 RPS |
| Овербукинг под конкуренцией | 0 (тест: 200 параллельных запросов на последнюю единицу → 1 успех) |
| Лаг индексации Elasticsearch | p95 < 5 с |
| Доставка события на дашборд склада | p95 < 2 с |
| AI-ответ (end-to-end) | p95 < 8 с, потоковая выдача |
| Доступность | 99.5% (учебная цель) |

### 9.2. Наблюдаемость

Каждый HTTP-запрос от Gateway получает Trace ID; трассировка проходит через Kafka (пропагация контекста) и внешние вызовы. Метрики: бизнес (заказы, овербукинг, loss ratio, конверсия) и технические (latency, ошибки, лаг консьюмеров). Логи структурированные, с Trace ID. Дашборды и алерты: лаг Kafka, ошибки платёжного порта, рост `EXPIRED`, `INSPECTION_OVERDUE`, срабатывания circuit breaker.

### 9.3. Безопасность и данные

- Проверка разрешений (`ресурс:действие`) на всех эндпоинтах каждого сервиса; принцип минимальных прав; поддержка совмещения ролей; политики SoD (3.4).
- Pre-signed URL с коротким TTL для файлов; клиент видит только свои файлы.
- Минимизация персональных данных (раздел 5.5.1); маскирование в логах.
- Аудит-лог неизменяем; записывает пользователя, действие и разрешение, давшее доступ; доступен ролям `AUDITOR`, `ADMIN`, `SUPPORT_AGENT` (в пределах своих задач). Финансовые журналы фондов — append-only.
- Защита от злоупотреблений: rate limiting, лимиты на число неудачных оформлений, детект подозрительных паттернов.

### 9.4. Тестируемость

Нагрузочные сценарии (k6/Gatling), хаос-сценарии (недоступность LLM, платёжного шлюза, Kafka, задержка консьюмера), контрактное тестирование событий и API, Testcontainers для интеграционных тестов.

### 9.5. Конфигурируемость

Все `CFG` в централизованной конфигурации; изменения аудируются; поддерживаются feature flags (`protection_plan.enabled` и др.).

## 10. Юридический и комплаенс-контекст (для реалистичности, требует заключения юриста)

Для учебного проекта эти пункты задают ограничения на модель данных и процессы, но не требуют реальных согласований.

- **Персональные данные (РФ):** хранение в инфраструктуре на территории РФ, согласие на обработку, минимизация (не хранятся сканы паспортов), сроки хранения актов и фото `CFG`.

- **Оферта и ПЭП:** договор-оферта с материальной ответственностью, порядок ПЭП по SMS, согласие на списание с карты при просрочке и повреждении.

- **Фискализация и эквайринг:** учитываются как внешние зависимости (порты).
- **Ограничение ответственности платформы** при овербукинге и компенсации фиксируется в оферте.

## 13. Критерии приёмки ключевых сценариев

**S1. Конкурентное бронирование.**
Дано: у SKU одна свободная единица на выбранные даты. Когда: 200 клиентов одновременно начинают оформление. Тогда: ровно один получает резерв, остальные получают отказ с предложением альтернативных дат; ёмкость не уходит в минус.

**S2. Истечение резерва.**
Дано: клиент начал оформление и не завершил оплату. Когда: проходит TTL. Тогда: заказ → `EXPIRED`, ёмкость возвращена, холд (если был) снят, клиент уведомлён.

**S3. Цена и наценка спроса.**
Дано: на день D забронировано >80% ёмкости категории. Когда: клиент начинает оформление на даты, включающие D. Тогда: цена дня D включает +30%, остальные дни без наценки; цена зафиксирована на TTL. При продлении наценка не добавляется.

**S4. Смена грейда и овербукинг.**
Дано: единица достигла 50 Wear Days, пул A стал меньше числа броней. Когда: система обнаружила несоответствие. Тогда: вытесняется последняя бронь (по правилу 5.8), клиенту предлагается лестница; при отказе от всех вариантов — возврат 100% и бонус.

**S5. Очная выдача.**
Дано: заказ `RESERVED`, серийные номера назначены. Когда: кладовщик сканирует единицы и сверяет личность клиента. Тогда: подписан акт с фото «до», единицы `IN_USE`, заказ `ACTIVE`; скан паспорта не сохранён.

**S6. Просрочка возврата.**
Дано: заказ активен, возврат просрочен на 5 часов. Когда: срабатывает биллинг. Тогда: попытка списать 50% суточной стоимости с карты; при отказе — из холда; при нехватке — уведомление о долге, заказ → `DISPUTED`. Если следующая бронь на ту же SKU ближе 12 часов — запускается процедура овербукинга.

**S7. Нарушение SLA инспекции.**
Дано: единица в `RETURNED_PENDING_INSPECTION` более 4 рабочих часов. Когда: срок истёк. Тогда: эскалация менеджеру, метка `INSPECTION_OVERDUE`, единица остаётся вне аренды; холд снимается не позднее 72 часов после возврата.

**S8. Износ.**
Дано: аренда 10 суток (фактических). Когда: заказ завершён. Тогда: начислено 12 Wear Days (10 × 1.2). При переходе `total_wear_days` через 50 единица получает `COSMETIC_WEAR` и переходит в грейд B; при `service_wear_days` ≥ 100 после возврата статус принудительно `MAINTENANCE`.

**S9. AI-подбор с проверкой совместимости.**
Дано: запрос «звук для подкаста на двоих», LLM предложил несовместимый набор. Когда: обработка. Тогда: матрица заменяет позиции на валидные, клиент видит объяснение; при недоступности LLM срабатывает fallback без ошибки для клиента.

**S10. Высокий риск.**
Дано: TAV > 500 000 ₽, клиент уровня L2. Когда: клиент оплачивает. Тогда: заказ → `PENDING_REVIEW`, модератор связывается с клиентом; после одобрения → `RESERVED`; договор подписывается очно на выдаче; при отказе — отмена, холд снят, ёмкость возвращена.

**S11. Совмещение ролей.**
Дано: пользователь с ролями `WAREHOUSE_OPERATOR`, `WAREHOUSE_SUPERVISOR`, `RISK_MODERATOR`. Когда: он открывает рабочее место. Тогда: видит задачи по всем трём функциям. Когда: пытается модерировать, проверять или разрешать претензию по заказу, где он клиент. Тогда: действие заблокировано. Когда: утверждает претензию выше порога по инспекции, которую проводил сам. Тогда: создаётся запрос второму утверждающему; если такого пользователя нет — действие разрешено в режиме `LOG_ONLY` с комментарием, флагом в аудите и алертом владельцу.

**S12. Амортизация и фонды.**
Дано: единица со стоимостью 300 000 ₽, остаточной 30%, сроком 500 Wear Days, ставкой ремонта 120 ₽. Когда: завершена аренда 5 суток. Тогда: начислено 5 Wear Days; в F1 записано 2 100 ₽, в F2 — 600 ₽; балансовая стоимость уменьшена на 2 100 ₽; повторная доставка события не создаёт дубликатов. Для аренды 10 суток начислено 12 Wear Days и 5 040 ₽ в F1.

**S13. Расчёт цены с защитой.**
Дано: пример из 5.3.3. Когда: клиент начинает оформление. Тогда: показаны цены по дням, наценка спроса, строка защиты 756,84 ₽, итог 11 568,84 ₽ и холд 30 000 ₽ отдельно; цена зафиксирована на TTL.

**S14. Изменение тарифа.**
Дано: подтверждённые брони и новый тариф с датой вступления в силу. Когда: тариф вступил в силу. Тогда: существующие брони сохранили зафиксированные цены, новые оформления считаются по новому тарифу; событие `TariffChanged` опубликовано, изменение записано в аудит.
